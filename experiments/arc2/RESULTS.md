公式公開データでの固定条件評価を完了しました。公開評価は 8 秒条件で **0/120 問**、
同じコードの 32 秒条件で **1/120 問、1/167 出力（0.60%）**です。
実行と再評価の基盤は動作していますが、競争力のある性能には達していません。

## 固定条件

- Python 3.12.14 / NumPy 2.3.5、CPU のみ。
- 1 問 8 秒または 32 秒、最大 4000 状態、beam 幅 32、Python 深さ 3。
- C++ 時間配分 0.6、プロセス仮想メモリ上限 768 MiB、深さ 1 → 2 → 3。
- 学習側 8 秒は 2 分割、公開側 8 秒は 4 分割、公開側 32 秒は 8 分割。
  各 run 内で互いに重ならない問題を並列実行。
- 公式データ固定コミット: `f3283f727488ad98fe575ea6a5ac981e4a188e49`。
- 各 run の開始・終了で 48 ファイルの同一 SHA-256 を確認。
- 3 回の run 間でも推論ソースの SHA-256 が一致。公開側 2 回のデータ SHA-256 も一致。

32 秒条件は、8 秒の結果と時間切れの頻度を確認した後で宣言して行った予算比較です。
新しい独立 holdout 評価とは扱いません。公開評価の正解を使った規則や候補順位の調整はしていません。
CPU の時間制限を使うため、並列度や実行環境の負荷によって探索範囲と予測は変わり得ます。
run 全体の所要時間は並列度が違うので、そのまま速度比較には使えません。

## 実行と時間切れ

3 回の run の延べ 340 問すべてで runner は正常終了しました。全 task ID と全 test 入力に
2 個の attempt フィールドが保存されています。公開側の C++ 深さ 3 は、8 秒条件では
2 件完了・156 件時間切れ、32 秒条件では 57 件完了・110 件時間切れでした。
この件数は問題数ではなく、test 入力ごとの深さ 3 の実行数です。
探索の時間切れと提出ファイル作成の失敗は別です。前の深さで得られた候補を保持し、候補不足時は
Python 側の予測または入力コピーの保険を使います。

予算増加によって深い探索を完了できる test 入力は増えましたが、正解は 1 出力に留まりました。
この結果だけでは、さらに時間を増やせば十分な精度が得られるとは判断できません。

## 再現する設定

Notebook と CLI の既定値は 8 秒です。32 秒の測定条件は、他の設定を変えずに
`--seconds-per-task 32` を指定します。Notebook では実行セルより前に
`os.environ["ARC2_SECONDS_PER_TASK"] = "32"` を設定します。

今回の 32 秒の分割評価コマンドは次のとおりです。

```bash
python tools/benchmark.py --tasks /path/to/ARC-AGI-2/data/evaluation --output reports/public120_32s --shards 8 --seconds-per-task 32 --max-states 4000 --backend hybrid
```
